`policy.routes` is an array of route bindings. Each binding **matches** a set of OpenAPI operations and contributes a check, required scopes and/or a backend credential to every operation it matches. An operation can be matched by any number of bindings, and they stack:

- every operation must be matched by **at least one binding with a `check`** — listing an operation in OpenAPI implies no policy, and there is no permissive fallback;
- every matching binding's `check` must pass, in configuration order;
- every matching binding's `required_scopes` are required;
- exactly one backend credential is resolved per operation (see [backend resolution](#backend-resolution)).

Uncovered operations, unknown selectors, matchers that select nothing and unresolvable backends all fail startup.

## Route bindings

```json title="config.json"
{
  "policy": {
    "definitions": {
      "has_subject": { "cel": "claims.sub != ''" },
      "publisher": { "cel": "claims.sub == params.subject" },
      "amount": { "file": "policies/amount.cel" }
    },
    "routes": [
      {
        "name": "baseline",
        "match": "*",
        "check": { "ref": "has_subject" },
        "auth": { "backend": "read" }
      },
      {
        "name": "publish_item",
        "match": { "operation_id": "createItem" },
        "check": {
          "all": [
            { "ref": "publisher", "params": { "subject": "alice" } },
            { "ref": "amount", "params": { "max": 5 } }
          ]
        },
        "auth": { "backend": "write", "required_scopes": ["items:write"] },
        "on_deny": {
          "response": { "status": 403, "code": "package_denied", "detail": "Publishing policy denied this item." },
          "log": { "reason": "publishing_policy", "level": "warn", "message": "publishing policy denied" }
        }
      }
    ]
  }
}
```

Here every operation requires a subject and uses the `read` credential, and `createItem` additionally runs the publishing check and uses `write`.

### `match`

Either the string `"*"` (every operation) or an object. All keys in one object must hold; list values match **any** of their entries.

| Key | Selects operations… |
| --- | --- |
| `operation_id` | with this `operationId`, or any in a list. |
| `method` | with this HTTP method, or any in a list. |
| `path` | with exactly this OpenAPI path **template**, e.g. `/items/{id}`, or any in a list. Works for operations without an `operationId`. |
| `path_prefix` | under this template prefix, compared by whole segments: `/admin` matches `/admin` and `/admin/users/{id}`, not `/administrators`. |
| `tag` | carrying this OpenAPI tag, or any in a list. |
| `extension` | whose OpenAPI vendor extensions equal every given value, e.g. `{ "x-tier": "internal" }`. |
| `all` / `any` / `not` | combining nested matchers, like [rules](#rules). |

```json
{ "match": { "operation_id": ["listItems", "getItem"] } }
{ "match": { "path": "/items/{id}", "method": "GET" } }
{ "match": { "tag": "admin", "method": ["POST", "PUT", "DELETE"] } }
{ "match": { "path_prefix": "/internal", "not": { "operation_id": "healthCheck" } } }
{ "match": { "any": [{ "tag": "billing" }, { "extension": { "x-pii": true } }] } }
```

Matching runs once at startup against the OpenAPI document, so it costs nothing per request. An unknown `operation_id`, `path` or `tag`, or a matcher that selects no operations, fails startup.

<Callout type="warn" title="Broad matchers apply to new endpoints">
  A binding matched by `"*"`, a tag, a prefix or an extension also covers operations added to the spec later — they inherit its check and backend without a config change. If you want every new endpoint to fail startup until someone reviews it, make sure each operation's only `check` comes from a binding that names it by `operation_id` or `path`. Use [`-explain`](#explaining-the-effective-policy) to review what each operation inherits.
</Callout>

### `check`

The rule that must evaluate to `true` for the request to be forwarded. See [rules](#rules) below. A binding may omit `check` when it only sets `auth`, but every operation needs at least one matching binding that has one. Write `{ "cel": "true" }` to allow every authenticated caller explicitly.

### `auth`

`auth.backend` selects the upstream credential:

| Value | Meaning |
| --- | --- |
| `"none"` | Forward **no** `Authorization` header upstream. |
| `"forward"` | Forward the caller's verified bearer token unchanged. |
| `"default"` | Use the top-level `backend_auth` credential. |
| _profile name_ | Use the named profile from `backend_auth_profiles`. |

A binding may leave `auth.backend` out and inherit it from a broader binding. `auth.required_scopes` is an optional **all-of** list; the scopes of every matching binding are checked before any check runs. See [backend authentication](/backend-auth).

### Backend resolution

Each operation uses exactly one backend. Among the matching bindings that set `auth.backend`, the **narrowest** wins: a binding whose selected operations are a strict subset of another's overrides it. This does not depend on the order of bindings, so the common layering just works:

```json
[
  { "match": "*", "check": { "ref": "has_subject" }, "auth": { "backend": "read" } },
  { "match": { "tag": "admin" }, "auth": { "backend": "admin" } },
  { "match": { "operation_id": ["createItem", "deleteUser"] }, "auth": { "backend": "write" } }
]
```

When the narrowest candidates overlap without one containing the other — say, operations tagged both `admin` and `billing`, with different backends — and they disagree, startup fails and names both bindings. Settle it with a binding that matches exactly the overlapping operations; it is narrower than both. Bindings that agree never conflict.

### `params`

Binding-level parameters, available to expressions as `params`. A `ref` that carries its own `params` overrides them within that reference.

### `on_deny`

Customize what happens when the check evaluates to `false`:

- `response.status` — `401`, `403` (default) or `404`.
- `response.code` and `response.detail` — bounded static text returned in the problem document.
- `log.reason`, `log.message` and `log.level` (`info`, `warn`, `error`) — customize the [audit event](/audit).

<Callout type="warn" title="Static text only">
  Never interpolate caller input into denial text or logs.
</Callout>

`on_deny` applies whenever that binding's check returns `false`, including when any child of an `all` fails. When several bindings match, the **first** binding whose check fails decides the response; later checks are not evaluated. **Errors** during evaluation or data lookup are not converted into custom denials: they fail closed with their own stable code, such as `policy_error` or `userinfo_unavailable`.

## Rules

`policy.definitions` holds named, reusable rules. Every rule — named or inline — specifies **exactly one** of:

| Key | Description |
| --- | --- |
| `cel` | An inline CEL expression. |
| `file` | A CEL file relative to the config (UTF-8, at most 64 KiB). |
| `ref` | A named rule from `definitions`, optionally with `params`. |
| `all` | Every child must be true. Short-circuits in order. |
| `any` | At least one child must be true. Short-circuits in order. |
| `not` | Negates one child rule. |

`all` and `any` require at least one child. Named rules may reference other named rules, but cycles and excessive expansion fail startup. A `ref` with `params` provides reuse without user-defined CEL functions or unbounded recursion.

Rules are compiled and type-checked **once, at startup**.

## Shared values

`policy.values` is a map available to every expression as `config`:

```json
{
  "policy": {
    "values": { "tenant": "blue" }
  }
}
```

```cel title="policies/amount.cel"
'tenant' in query && query['tenant'][0] == config.tenant &&
body.amount <= params.max
```

## Explaining the effective policy

Because bindings stack, the policy for one operation can come from several places. `-explain` prints it per operation and exits, without contacting the issuer:

```sh
go run -buildvcs=false . -config examples/config.json -explain
```

```text
POST /items (createItem)
  backend: write from routes[2] create_item
  scopes:  items:write (routes[2] create_item)
  checks:  routes[0] baseline → routes[2] create_item
```

Checks are listed in evaluation order. Commit the output, or diff it in review, to see exactly what a config change does to each operation.

## Limits

- Each CEL evaluation has a cost cap of 10,000 units.
- The expanded policy graph is limited to 256 nodes and 16 levels per binding.
- The whole configuration may compile at most 4,096 policy nodes and 4,096 matcher nodes, with matchers nested at most 16 levels deep.

<Callout type="info" title="Legacy format">
  The earlier `policy.default` / `policy.operations` format is deliberately rejected. Migrate to route bindings.
</Callout>
