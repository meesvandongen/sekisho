A _sekisho_ (関所) was a checkpoint on the highways of Edo-period Japan. Travellers had to present a pass, state their business, and satisfy the guards before they could continue down the road. **Sekisho** does the same for your API.

It sits in front of a single upstream service, and every request travels the same six stations. A request that fails one is turned back with a stable [outcome code](/outcomes) — and nothing reaches your upstream.

<Stations />

<Callout title="No implicit allow">
  Routes missing from the OpenAPI document are always rejected. Every declared operation must be covered by at least one policy check and resolve to exactly one backend, or the gateway refuses to start — there is no permissive fallback. Every request that gets through has passed rules you wrote.
</Callout>

## Why Sekisho

- **Explicit by construction.** The spec, the bindings and the policies must agree at startup, so an endpoint is only reachable once a policy covers it. Bind operations by name to make every new endpoint fail startup until reviewed, or match by tag, prefix or `"*"` to apply rules broadly.
- **Lazy and cheap.** Request bodies, userinfo and introspection are fetched only when a selected CEL branch actually needs them; everything else streams.
- **Least privilege upstream.** Routes pick named backend credentials, so read traffic never carries a write token. The caller's token is forwarded only where a route opts in.
- **Testable offline.** Run your policies against JSON fixtures in CI without an issuer, network or secrets.
- **Observable.** Stable outcome codes, a structured audit trail, and compile-time OpenTelemetry instrumentation.
